## [0.13.0] — 2026-08-15

### Changed

- **`@ospex/sdk`: `contests.list` now decodes its wire body through the zod `parseWire()` boundary.** A mistyped field in a list response — e.g. a non-string `gameFinalType` — throws a typed `OspexValidationError` (with the dotted field path and the `ZodError` as `cause`) instead of propagating verbatim into the public `Contest` and, through it, the CLI's agent JSON payload. The schema enumerates exactly the fields the list mapper copies and keeps the documented tolerances (unknown keys stripped; the pre-#41 settlement trio and the optional start-time companions / `gameFinalType` stay optional), so a well-formed body from any supported core-api build decodes exactly as before. The detail read (`contests.get`) keeps its existing decode; extending the boundary there is a separate change.

### Added

- **`@ospex/sdk` + `@ospex/cli`: dated historical contest discovery — `contests.list({ date })` / `ospex contests list --date YYYY-MM-DD`.** The listing window becomes that UTC day `[00:00Z, next day 00:00Z)` instead of the forward-only hours window, so an agent can enumerate a past day's contests for the postgame settle-and-claim half of its lifecycle, signer-free. Dated rows carry a new optional `Contest.gameFinalType` — the linked game's upstream result status (`games.final_type`) verbatim (`'Finished'` / `'Postponed'` / … free text, `""` sentinel); the CLI human table adds a `finality` column in dated mode and the `--json` envelope payload carries the field through. `date` and `hours` are mutually exclusive — the CLI refuses the pair before any client work and the API refuses it with a 400. Additive: default (no-`date`) listings are unchanged, the key is absent (not `undefined`-assigned) on non-dated rows, pinned by tests in both directions. Requires a core-api build serving `GET /v1/contests?date=`. A pre-`date` core-api build ignores unknown query params, so a dated call against one returns the ordinary forward window with no `gameFinalType` keys — a consumer that must distinguish the two can check for the key's presence.

## [0.12.0] — 2026-08-02

### Added

- **`@ospex/sdk`: contest and game reads now surface the start-time companion fields core-api serves alongside `matchTime`.** `Contest`, `SpeculationParentContext`, and `ContestUpdate` gain optional `chainStartTime` / `gameMatchTime` / `gameEarliestMatchTime` (ISO-8601 strings with the contest surfaces' `""` sentinel convention); `Game` gains optional `gameMatchTime` / `earliestMatchTime` (the latter `string | null` — the games endpoint's nullable convention). `matchTime` itself is unchanged everywhere and remains the conservative bound to gate on; the new fields are its raw inputs — `gameEarliestMatchTime` / `earliestMatchTime` is the game's retained start-time safety floor, served verbatim (it is not guaranteed `<= gameMatchTime`). Carried on snapshots **and** stream deltas alike (`contests.subscribe` bodies and the `contestId`-scoped snapshot projection), so a floor raise or feed reschedule reaches subscribers without a re-fetch. All fields are optional and conditionally copied: against a core-api build that predates them the keys are absent (not `undefined`-assigned), pinned by tests in both directions. Additive — no existing field changes shape or meaning.

### Removed

- **BREAKING — `@ospex/cli` + `@ospex/sdk`: `commitments submit-raw` / `commitments.submitRaw` no longer default `expiry` to `now + 24h`. An explicit expiry is now required.** The default was a wall-clock offset with no relationship to when the game starts. `submitRaw` takes a raw protocol tuple and performs **no contest read of any kind**, so it never had a match time to derive a safe value from — the 24h offset was a guess, and for a commitment signed shortly before first pitch it left a live, matchable order deep into in-play. `MatchingModule`'s NatSpec makes `expiry` the sole temporal guard on a commitment and states that off-chain infrastructure is responsible for setting sensible defaults; a blind offset discharges that responsibility by guessing, so the default is removed rather than documented as a footgun. `RawSubmitArgs.expiry` stays **typed optional** (`expiry?: bigint`) so no consumer breaks at compile time, and the enforcement is a runtime `OspexValidationError({ field: 'expiry' })` raised **before any signer access, chain read, or POST** — nothing is signed and nothing is submitted. The `ospex commitments submit-raw` CLI raises the same typed error in its **pre-parse, before `getClient`**, so a forgotten flag never costs a keystore passphrase prompt or a signer unlock. **`commitments submit` / `prepareSubmit` are unaffected** — they read the contest and already default expiry to its match time, which is the surface to reach for if you want a default. Callers that already pass an explicit expiry (including `ospex-market-maker`, which always does) are unaffected.

### Changed

- **`@ospex/cli`: `submit-raw --expiry` accepts duration strings and throws a typed error.** The flag previously accepted only unix-seconds or ISO-8601 and rejected malformed input with a bare `Error`, while the high-level `commitments submit --expiry` accepted `"30m"` / `"4h"` / `"1d"` / `"1w"` as well. With `--expiry` now mandatory on `submit-raw`, that asymmetry would have forced every caller of the raw surface to compute a timestamp by hand, so the two flags now take the same forms; bad input raises `OspexValidationError({ field: 'expiry' })` like every sibling validation surface. **A duration resolves against the caller's clock at parse time**, so a re-issued `submit-raw` with the same duration signs a different `expiry` → a different commitment hash → the server's hash-keyed idempotency cannot dedup it; pass the absolute unix-seconds value you originally signed to make a retry idempotent (`docs/AGENT_CONTRACT.md` §7).

### Fixed

- **`@ospex/sdk`: the two `--expiry` upper-bound errors now state the bound each actually enforces.** `validateExpiry` (the `submitRaw` path) caps at **366 days** and `parseExpiry` (the `submit` / `prepareSubmit` path) caps at **365 days**, but both messages read "1 year" — so an expiry between the two was accepted by one surface and refused by the other while both explained the refusal with the same wrong number. The messages now read "more than 366 days in the future" and "within 365 days of now" respectively, and both constants carry a comment naming the discrepancy. **Behaviour is unchanged**: this corrects the wording only. Reconciling the two values is a follow-up. Each message is now pinned by a test that reads the day count **out of the message** and probes the validator at that exact boundary (cap accepted, cap + 1 refused), then asserts the number is 366 / 365 — so a reverted message, a moved constant, or the two drifting apart all turn red.
- **Docs: `commitments submit-raw` was missing from the `--yes` contract in `docs/AGENT_CONTRACT.md` §3.** That section enumerates the commands requiring `--yes` for non-interactive runs and omitted `submit-raw`, so its bolded catch-all — "Other write commands sign and send WITHOUT requiring `--yes`" — covered it, wrongly; the quick-reference cheat sheet repeated the same untruth. `submit-raw` has always refused a non-TTY run without `--yes`: it has no preview-only mode, it always signs + posts, and the guard exists so a reactive USDC-approval prompt can never hang on a stdin nobody can answer. Unlike the three dual-mode commands (`submit` / `match` / `approvals setup`), **`--json` does not exempt it**. **No behaviour changed** — the runtime was always the stricter of the two; the documented contract now matches it. The release playbook's step 2.5.8 asserted the same untruth ("no `--yes`, so it goes straight through") and is corrected alongside.
- **`@ospex/sdk`: the own-state health docs named a `lagSource` value the server never sends, and a gate constant that does not exist.** `OwnStateHealth`'s JSDoc described `lagSource` as "currently `'sync_state'`, the indexer's per-block processed-watermark, which advances on every block" — wrong three ways. The server sends **`'indexer_cursor'`**; `sync_state` is an unpopulated legacy table (sourcing lag from it returned `INDEXER_CURSOR_UNAVAILABLE` on every request until core-api repointed it); and the cursor is written **per processed block-range chunk**, not per block. Separately, four docstrings told consumers to fold `indexerLagSeconds < INDEXER_LAG_MAX` into a stream-health gate — **`INDEXER_LAG_MAX` exists in no repo**. The reference market-maker's knob is `ownState.indexerLagMaxSeconds` (default 30s), polled once per runner tick (`auditPollIntervalMs`, default 60s — the docs' "~10 s" is that setting's configurable floor, not its cadence). The docs now also carry the property a threshold actually has to be sized against: because the cursor moves per chunk rather than continuously, the published value **sawtooths roughly 0 → 15s** while the indexer is caught up, so a threshold inside that band can read as degraded on a perfectly healthy indexer depending on when the sample lands. **No behaviour change and no type change** — `lagSource` stays a plain `string` rather than a literal union, so the server can name a different signal without that being breaking. The four test fixtures asserting `lagSource: 'sync_state'` now use the value the server actually sends, so the suite exercises the real wire shape. Corrected at the source in `ospex-core-api`.

## [0.11.0] — 2026-07-28

### Fixed

- **`@ospex/cli`: `--risk-usdc` on `commitments match` / `commitments fillability` no longer applies the maker's 100-wei6 lot rule to the taker's desired risk.** Both commands parsed the flag through `usdcDecimalToWei6`, which enforces `wei6 % 100 === 0` — a rule `MatchingModule._validateCommitment` imposes on a maker's **signed `commitment.riskAmount`** and on nothing else. `matchCommitment`'s only direct guard on `takerDesiredRisk` is a zero check; the maker leg it derives is floored to the lot by the contract itself. Two consequences, both reproduced: **(a) the CLI rejected values it had just printed** — a preview's `economics.takerRiskUSDC` is `min(takerDesiredRisk, fillMakerRisk × (oddsTick − 100) / 100)`, which lands on the 100-wei6 grid only by coincidence, so `ospex commitments match <hash> --json` could report `takerRiskWei6: 999936` and `--risk-usdc 0.999936` would then be refused, making it impossible to bind an execution to an already-validated preview; and **(b) at low odds the constraint was outright unsatisfiable** — the taker amounts producing a given fill span a window only `profitTicks` wide, so below decimal odds 2.00 that window need not contain any multiple of 100; for `oddsTick` 101–150 (decimal 1.01–1.50) even the minimum 100-wei6 fill has *no* lot-aligned taker amount at all, and at `oddsTick` 101 the entire valid window is `[1, 1]` wei6. A new `usdcDecimalToAmountWei6` performs the same strict parse — plain decimal, ≤ 6 fractional digits, must be positive — without the lot assertion, and the two taker call sites plus `fillability` use it. The maker path (`prepareSubmit` → the signed `riskAmount`) still uses `usdcDecimalToWei6` and still refuses off-grid input; that is now pinned by a test.
- **`@ospex/cli`: USDC allowance prompts no longer refuse their own suggested default.** All three interactive approval prompts (`commitments match`, `submit`, `submit-raw`) offer `wei6ToDecimalUSDC(required)` as the default and parsed the reply with the maker-risk parser. On `match`, `required` **is** the taker's risk, so the default is routinely off the lot grid — at `oddsTick 250` a taker desiring 200 wei6 fills 100 and owes 150, making the suggested default `0.000150`. Pressing Enter to accept it threw, was caught by a `catch` that reports every failure as a parse error, and exited 1 with `Could not parse "0.000150" as a USDC amount.` and no way forward but typing `max`. An ERC-20 `approve` amount has no protocol lot rule, so all three prompts now use `usdcDecimalToAmountWei6`.
- **`@ospex/sdk`: `computeSubmitYouView`'s counterparty cross-check could never fail.** The backfill re-derives the hypothetical taker's risk with integer math and compares it against the published `economics.counterpartyRiskUSDC` to catch silent drift. It parsed that string with the maker-risk parser, which threw on every sub-lot value — and the counterparty's risk is sub-lot in a large share of honest previews (at `riskWei6: 100n, oddsTick: 101` it is `"0.000001"`). The `try`/`catch` added to absorb those throws caught `OspexValidationError`, which is also the type of the drift error thrown inside the same `try`, so a genuine disagreement was swallowed along with the parse failures. With the correct parser the compensating `catch` is unnecessary and is removed; the check now actually fires. Both halves are pinned: an honest sub-lot preview is accepted, and a spliced `counterpartyRiskUSDC` throws.
- **BREAKING — `@ospex/cli`: `ospex approvals setup` no longer treats an explicit numeric zero as "leave unchanged"; it refuses the input.** `parseUsdcInput` collapsed a parsed raw zero into the same `{ kind: 'skip' }` variant as an omitted flag, so `--risk-usdc 0 --fee-usdc 0 --yes --json` exited `0` with a green `approvals.setup` execute envelope, `payload.plan.willSendCount: 0`, empty `results`/`effects` — while both allowances stayed live. In ERC-20 terms `approve(spender, 0)` is the canonical revoke, so that green envelope reads as proof of a revocation that never happened; it was relied on as exactly that during a mainnet rollback rehearsal. An explicit `0` (`"0"`, `"0.0"`, `"0.000000"`) on either dimension now throws a typed `OspexValidationError` naming the flag that was passed and pointing at the two real revocation surfaces — `ospex commitments approve 0` for the PositionModule allowance, a direct USDC `approve(TreasuryModule, 0)` for the TreasuryModule allowance. The refusal fires in the command's pre-parse, **before** any keystore passphrase prompt, signer unlock, chain read, or transaction, and exits `1`. **Omitting a flag, passing `skip`, and passing an empty string remain the intentional leave-unchanged inputs.** An idempotent re-run of an already-satisfied request still emits the legitimate `willSendCount: 0` green envelope — that path is unchanged and is now the only way to get one.

### Changed

- **`@ospex/sdk`: `usdcDecimalToAmountWei6` is a new barrel export, and `usdcDecimalToWei6`'s lot-size message names what the rule constrains.** The message previously read "…required by MatchingModule", which is true of a commitment's signed `riskAmount` but read as a claim about whatever value the caller happened to pass; it now says "…MatchingModule requires for a commitment's signed riskAmount". **Agents decoding USDC amounts out of `--json` envelopes should read the paired integer with `BigInt()` where one exists, not re-parse the decimal string** (`<name>USDC` ↔ `<name>Wei6`; inside `you` / `counterparty` the pair is `{ wei6, usdc }`). Not every field has a pair, and **the exception set differs per envelope** — `MatchPreview` has three, `SubmitPreview` five, and the top-level envelope uses a third convention (`requiredWei` / `requiredHuman`). So the rule is non-exhaustive: use the paired integer where one exists, otherwise follow that field's own contract. Do not assume an unpaired field is positive: a fee-disabled chain (`makerCreationFeeWei6: 0n`) or a risk small enough that profit floors to zero yields `'0.000000'`, which no parser accepts. Every unpaired field except `outcomes[].payoutUSDC` has an exact integer source elsewhere in the same payload (`you.profit.wei6`, `counterparty.risk.wei6`, `creationFee.makerShareWei6`, …) — use that. `outcomes[].payoutUSDC` is SIGNED on `'lose'` rows and has no integer source. `docs/AGENT_CONTRACT.md` enumerates both preview envelopes, and each list is pinned by a test. — `docs/AGENT_CONTRACT.md` promised that `you` / `counterparty` and preview USDC strings "round-trip with `usdcDecimalToWei6`", which was false for every off-grid amount, and merely renaming the parser would have left it false for zero: `wei6ToDecimalUSDC` is total, but both parsers validate user-supplied input and so refuse `'0.000000'` — a string the SDK really does emit (`creationFee.viewerShareUSDC` on any non-lazy speculation). The contract now points at the `*Wei6` field for decoding and scopes `usdcDecimalToAmountWei6` to positive typed amounts; the matching claims on `PerspectiveAmount` and `MatchPreview` name the correct parser. `usdcDecimalToWei6` keeps its name and behaviour unchanged so no existing caller is silently relaxed.
- **BREAKING — `@ospex/cli`: `approvals setup`'s two dimensions are fully orthogonal; the `--risk-usdc` → `--fee-usdc` auto-include is removed.** Passing `--risk-usdc` alone previously also targeted a 1 USDC TreasuryModule budget, so a caller asking to approve bet risk silently got a second approval they did not request, and `--fee-usdc 0` existed solely as the opt-out from that surprise — which is what overloaded zero with a "skip" meaning in the first place. Each flag now acts on its own spender and nothing else: an omitted dimension is left untouched, and no input to one flag can produce a send on the other. **This means a wallet that may be first to a market must now approve `--fee-usdc` explicitly.** The speculation creation fee is lazy — the first commitment match on a given market pulls 0.25 USDC from each side via TreasuryModule — so a maker opening a new line whose fee allowance does not cover its share will have that first match revert. Makers should carry a fee budget; a wallet that only ever takes already-created lines does not need one. `doctor` and the match-preview next-commands already emit `ospex approvals setup --fee-usdc <n>` as the remediation when that allowance is short. `docs/QUICKSTART.md` now documents the two dimensions as a table, states the first-to-a-market rule, and gains a **Revoking approvals** section covering both spenders.
- **`@ospex/cli`: `approvals setup` amount parsing now throws typed `OspexValidationError` rather than a bare `Error`.** Bad-shape input (`"1e3"`, `"5,000"`, `">6 decimals"`) previously threw an untyped `Error`, so the CLI printed `error: …` instead of `error (VALIDATION_ERROR): …` for this one path while every sibling validation surface was typed. Both the shape refusal and the new zero refusal carry `field` set to the originating flag (`--risk-usdc` / `--fee-usdc`), or `amount` for interactive input.

### Removed

- **BREAKING — `@ospex/cli`: `autoIncluded` is gone from the `approvals setup` plan-item shape.** It appeared on `PlanItem`, on the `--json` payload at `payload.plan.items[].autoIncluded`, and as the rendered sub-line `(auto-included alongside --risk-usdc; pass --fee-usdc 0 to skip)`. With no cross-dimension defaulting the field can only ever be `false`, so it is removed rather than retained as a constant. Consumers that read it should drop the read; nothing in the plan's meaning changes, and `spenderModule` + `action.kind` remain the discriminators.

## [0.10.1] — 2026-07-21

### Fixed

- **`@ospex/sdk`: `positions.claimAll` now closes the same-run settle→claim RPC-replica race without weakening other stop rules.** When a pending-settle entry is freshly settled by that sweep, claim-all requires the successful mined settle receipt and an authoritative on-chain `Closed` re-read before estimating the dependent claim. If that immediately-following claim still returns a pre-send `estimateGas` `CHAIN_ERROR` with no transaction hash or receipt, claim-all waits 10 seconds, confirms `Closed` again, and retries the claim exactly once. A second estimate failure, a claimable-only failure, nonce/fee read failure, broadcast/receipt ambiguity, or inclusion-time revert is not retried and remains a failed entry.

## [0.10.0] — 2026-07-04

### Added

- **`@ospex/sdk` + `@ospex/cli`: score-wait / score-status surface — `client.contests.{waitForScored, scoreStatus}` and `ospex contests {score --wait, wait-scored, score-status}`.** Scoring is asynchronous (a CRE oracle report flips the contest to Scored ~30–90s after `requestScore`), and previously the only way to observe it was to hand-poll `contests show`. Now: `client.contests.waitForScored(contestId, options?)` polls on-chain `ContestModule.getContest` (authoritative — not the core-api projection, which the indexer can lag) until the contest reaches Scored, returning `{ contestId, status, awayScore, homeScore }`; a **Voided** contest is terminal-for-scoring so it resolves immediately (never spins to the timeout), and the bounded poll throws a typed `OspexChainError` on timeout (never a sentinel). `client.contests.scoreStatus(contestId)` is a one-shot, signer-free read returning `{ contestId, status, scored, awayScore, homeScore }` — scores are gated on `status === 'scored'` and returned `null` otherwise, so a legitimate **0-0** final surfaces as real `0`s while a pre-score contest never presents a phantom 0-0. Both are reads (require `rpcUrl`, no signer) and share a new `readContestOnChain` helper with `waitForVerified` (widened to also read the away/home scores the `getContest` tuple already returns). New public type exports (importable from `@ospex/sdk`): `WaitForScoredOptions`, `WaitForScoredResult`, `ScoreStatusResult` — the root barrel now also re-exports the sibling contest-operation types (`WaitForVerifiedOptions`/`Result`, `CreateContestArgs`/`Result`, `ScoreContestArgs`/`Result`, `RequestMarketUpdateArgs`/`Result`) so the whole `client.contests` operation surface can be named without reaching into subpath modules. CLI: `ospex contests score <id> --wait` is **opt-in** (default stays fire-and-return, so existing agents/scripts are unaffected) — it sends `requestScore`, then polls to Scored; because the CRE score report rides a best-effort log trigger that can silently drop, on a first-window timeout it **re-requests scoring once** (idempotent + free, no cooldown) and waits a second window before surfacing a **single** failure envelope that preserves **every** `score-contest` tx it sent in `effects[]` — including a re-request (or the initial tx) that reverted (`status: 'reverted'`) or was broadcast-but-not-receipt-confirmed (`status: 'submitted'`), both `ok: false` — and points `nextCommands` at `wait-scored`. A Voided resolution is a success envelope carrying an info `contest-voided` warning. `ospex contests wait-scored <id>` (signer-free blocking poll, the read twin of `wait-verified`) and `ospex contests score-status <id>` (signer-free one-shot read) round out the surface; both flags accept `--timeout-seconds` / `--poll-interval-seconds`. Human score lines best-effort enrich actual team names + away/home roles from core-api (Team Identity Rule; non-fatal on lag), while `--json` payloads keep the raw on-chain numbers. Additive and backward-compatible — the `contests score` `--json` payload gains a `scoring` field (`null` unless `--wait` resolved).

## [0.9.0] — 2026-07-01

### Added

- **`@ospex/sdk` + `@ospex/cli`: `Speculation` now carries the settlement outcome — `winSide`, `settledAt`, and `voided`.** A read of a settled speculation (`client.speculations.get`/`list`, and the `speculations[]` embedded in `client.contests.get`/`list`) previously exposed only `speculationStatus` (`0` open / `1` closed) with **no way to tell who won**. `winSide` is the authoritative on-chain outcome — `'away'`/`'home'`/`'over'`/`'under'`/`'push'`/`'void'`, or `null` while open — and for spread/total/push/void it **cannot** be recomputed from the contest score client-side, so it is the field to route settlement on. `settledAt` is the ISO settlement timestamp (`null` while open); `voided` is `true` iff `winSide === 'void'`. **Invariant: `speculationStatus === 1` ⟺ `winSide !== null`** — core-api projects both from the same atomic row, so a closed speculation always carries its winner. New public type exports: `WinSide` (`'tbd' | 'away' | 'home' | 'over' | 'under' | 'push' | 'void'`) and `SettledWinSide` (the same minus `'tbd'`). `ospex speculations show` / `list` display a `winSide` column. Additive and backward-compatible; the fields are populated by a core-api carrying the matching projection (ospex-core-api #41) and degrade to `null`/`false` against an older server. `scoredAt` is **not** added to the speculation — it is a contest-level field, read it from `client.contests.get` (`scoredAt`).

## [0.8.0] — 2026-06-29

### Added

- **`@ospex/sdk` + `@ospex/cli`: contest market-line refresh via `client.contests.requestMarketUpdate({ contestId })` and `ospex contests update-markets <contestId>`.** Submits `CreOracleReceiver.requestMarketUpdate(contestId)` — the third CRE request entrypoint alongside create (verify) and score. **Permissionless and free** (no USDC fee, no allowance, no LINK): it bumps the contest's on-chain market request nonce and emits a `CreOracleRequested` log that an off-chain Chainlink CRE workflow resolves by fetching current odds and reporting the refreshed market lines back via the KeystoneForwarder (~30–90s later; poll `client.odds.snapshot(contestId)` / `ospex odds show`). The contest must already be **Verified** — the call reverts `CreOracleReceiver__ContestNotVerified` otherwise, which the SDK lets surface rather than pre-checking (mirroring `score`'s premature-revert handling). `requestMarketUpdate` returns `{ contestId, requestNonce, txHash, receipt }` — `requestNonce` (the new latest market nonce, the on-chain bond a downstream watcher matches against `CreReportProcessed`) is parsed from the `CreOracleRequested(requestType=1)` event emitted by CreOracleReceiver. New public exports: `RequestMarketUpdateArgs`, `RequestMarketUpdateResult` (from `client.contests`). The CLI command mirrors `contests score` — a `<contestId>` positional, the shared signer-option group, `--json` as output-format-only (it always sends a tx); the `--json` execute envelope carries `action: 'contests.update-markets'`, a single `market-update-contest` transaction effect, `payload.requestNonce`, and a `verify-contest-odds` next-command (`ospex odds show <contestId> --json`). It reuses the `OSPEX_SCORE_CONTEST_TX_GAS` outer-tx budget (both are light request txs). Additive and backward-compatible.

### Changed

- **BREAKING — `@ospex/sdk` + `@ospex/cli`: contest create/score migrated from Chainlink Functions to the R5 Chainlink CRE oracle.** Both are now permissionless calls to `CreOracleReceiver` (the `CRE_ORACLE_RECEIVER` slot) instead of the retired `OracleModule`. `client.contests.create({ gameId })` submits `createContestAndRequestVerify(rundownId, sportspageId, jsonoddsId)` — the caller pays only the USDC ContestCreation fee (allowance to TreasuryModule; read from `TreasuryModule.s_feeRates(0)`, 0-skippable). `client.contests.score({ contestId })` submits `requestScore(contestId)` — free (no fee, no allowance); it requires the contest to be Verified and reverts until its on-chain start time has passed. There is **no LINK, no Chainlink subscription, no EIP-712 script approval, and no encrypted secrets** — CRE execution is funded off-chain by the workflow owner. `CreateContestResult` / `ScoreContestResult` drop `requestId`; `CreateContestArgs` / `ScoreContestArgs` drop `subscriptionId` / `gasLimit`. `ApprovalRequirement.tokenSymbol` and `PreviewApproval.token` narrow to `'USDC'`; `AgentApprovalPurpose` drops `'contest-creation-link'` / `'contest-scoring-link'`; `AgentApprovalSpenderLabel` drops `'OracleModule'`; `EstimatedCosts` drops `linkFees`. The approvals + balances snapshots drop the LINK dimension (`ApprovalsSnapshot.link`, `BalancesSnapshot.link`/`linkAddress`, `ApprovalSpender` `'oracleModule'`). `ospex doctor` drops the `balances.link` + `allowances.link_oracle` checks and redefines `createContests` readiness for CRE (API + POL + USDC→TreasuryModule; probes `CreOracleReceiver` instead of `OracleModule`). Contest read types drop the Functions source-hash fields (`verifySourceHash` / `marketUpdateSourceHash` / `scoreContestSourceHash`). **Amoy (80002) is de-advertised** — removed from the `ospex init` network picker and from the README / QUICKSTART; the `ChainId` / `Network` type plumbing still carries `80002` (power-user escape hatch via `OSPEX_CHAIN_ID`), but nothing steers users there. (`requestMarketUpdate`, a new permissionless CRE capability with no Functions predecessor, is now implemented — see the Added entry above.)

### Removed

- **BREAKING — `@ospex/sdk`: the entire Chainlink Functions surface is gone (clean break, no deprecation stubs).** Removed exports: `OspexScriptApprovalError` + `OspexScriptApprovalReason`, `OspexSubscriptionError` + `OspexSubscriptionReason`, `ScriptApproval`, `ApprovedScripts`, `AgentLinkFee`, `LinkAllowances`. - **`client.ownState.subscribe` handlers now receive an `OwnStateEventMeta { cursor }`** — the opaque SSE-level cursor AFTER the event the meta accompanies — as a **second argument** on `onSnapshot` / `onCommitment` / `onFill` / `onPositionStatus`, and as the **only argument** on `onReady` (which carries no body). ## [0.5.0] — 2026-05-29

Owner-authenticated maker view (`client.ownState`), public commitment type split, and the canonical signed-cancel primitive — the SDK side of the own-state SSE migration. **Two breaking changes** for SDK consumers, both pre-1.0 minor-bump per the file header convention; see the explicit migration notes below.

### SDK (`@ospex/sdk`)

#### Owner-authenticated own-state surface

- **New `client.ownState.snapshot({ address, cursor? })` — one-shot owner-auth REST consumer of `GET /v1/own-state/snapshot?cursor=`.** Returns ONE page of the locked `OwnerStateSnapshot { cursor, commitments, positions, truncated, positionsTruncated }`. Mints a fresh stream-auth bearer per call (challenge → EIP-712 sign over `OspexStreamAuth` typed-data → token), so single-shot callers pay the mint cost up front. **Callers needing the full commitment set MUST loop while `snapshot.truncated === true`, passing back `snapshot.cursor` on each call** — a single-page read can omit higher-`row_updated_at` rows AND a one-call read of "the maker's full book" is a footgun for nonce-floor / cancel-all derivation (computing `max(nonce) + 1` from the first page only can leave higher-nonce hidden commitments live). `positionsTruncated:true` is partial-visibility for the position list (snapshot helper hit its 200-row cap); there is no snapshot paging mechanism for positions and consumers should reach for `client.positions.*` for operator-side full history.
- **New `client.ownState.getCommitment({ address, hash })` — SNAPSHOT-SCOPE recovery helper, NOT an arbitrary owner-auth lookup.** Pages the owner-auth snapshot internally (mints exactly one bearer regardless of page count), searching each page for the requested hash. Returns the full `OwnerCommitment` on a hit OR `null` once a page with `truncated:false` has been scanned without finding it. **`null` means "outside the drained snapshot scope" (active + recently-terminal-since-prior-cursor), NOT "doesn't exist anywhere"** — a commitment whose only terminal transition is a long-past passive expiry will not be in scope and `null` is the correct answer for it. Throws `OspexOwnStateError({ reason: 'scan_limit_exceeded', pagesScanned: 50 })` when the defensive page bound fires while the server is still returning `truncated:true` — the result is UNKNOWN, NOT `null`; callers must distinguish (drive `snapshot()` manually, wait for the dedicated by-hash endpoint, raise the bound). Intended for low-frequency recovery (e.g. an MM needing to recover the signed payload for a commitment it knows it owns but lost from local state); arbitrary owner-auth-by-hash over full history is the right job for a future `/v1/own-state/commitments/:hash` endpoint.
- **New `client.ownState.subscribe({ address }, handlers)` — composite owner-auth SSE consumer for `/v1/stream/own-state`.** Handlers (all optional): `onSnapshot` (fires per snapshot page — cold-start inline frame + each REST page when the cold-start was `truncated:true`), `onReady` (fires once per connection after the final untruncated snapshot OR after server resume catchup — the "safe to trade" signal), `onCommitment` (full `OwnerCommitment` payload regardless of `book_visible`), `onFill` (Fill body, both maker-side and taker-side), `onPositionStatus` (`PositionStatusEvent` with the wider `PositionLifecycle` enum that adds terminal `settledLost` / `void` beyond `OwnerPosition.status`), `onStatus` (`'connected' | 'reconnecting' | 'degraded' | 'resync'`), `onError` (transport errors — non-fatal by default; fatal cases surface as `OspexStreamError({ reason: 'fatal' })` and end the subscription, see below). Token lifecycle is internal — the SDK caches the bearer, refreshes ~120 s before expiry NON-INTERACTIVELY (BYO posture — `KeystoreSigner`'s passphrase already resolved), and re-mints on 401 mid-attempt. Reconnects with `Last-Event-ID = running cursor`; server-side `event: resync` synchronously drops the running cursor → next reconnect is a cold-start; server-side `event: degraded` AND 3 consecutive failed reconnect attempts both emit `onStatus('degraded')` (transport keeps retrying — consumers enter quote-hold per spec §2.6 until the next `connected`). Truncated cold-start handoff drains REST `/v1/own-state/snapshot?cursor=` up to 50 pages emitting `onSnapshot` per page, then reconnects SSE with the final `k='live'` cursor as `Last-Event-ID`. **`onReady` MUST NOT fire on a partial baseline** — a truncated snapshot frame does NOT advance the running cursor (it's stashed in a separate pending-paging field) so a REST paging failure clears state cleanly and the next attempt cold-starts rather than resuming from an incomplete page-* cursor. Persistent truncation (50 REST pages still truncated) throws fatal via `onError({ reason: 'fatal' })` + subscription stops. `Subscription.unsubscribe()` is the ONLY close path — handlers NEVER fire after `await sub.unsubscribe()` returns; every async re-entry checks the closed flag before dispatching to a consumer handler, and the reconnect loop has a top-level try/catch that promotes any leak to `onError({ reason: 'fatal' })` rather than escaping as an unhandled rejection.
- **New public types** (all root-barrel exported from `@ospex/sdk`): `OwnerCommitment` (`ownerAuthorized: true` discriminator + `visibility: 'visible' | 'hidden'` from `bookVisible`; same `isLive` predicate as `PublicVisibleCommitment` so a maker can reuse one matchability check across anonymous + owner-auth payloads), `OwnerPosition` (discriminated by `status: 'active' | 'pendingSettle' | 'claimable' | 'claimed'` with the per-status metadata fields), `OwnerStateSnapshot`, `OwnStateSnapshotOptions`, `OwnStateGetCommitmentOptions`, `OwnStateSubscribeOptions`, `PositionLifecycle` (wider enum than `OwnerPosition.status`), `PositionStatusEvent`, `OwnerStateSubscribeHandlers`, `OwnerStateSubscribeStatus`, `OwnerStateResyncReason`, `OwnerStateDegradedReason`. New error class `OspexOwnStateError` + `OspexOwnStateReason` (currently only `'scan_limit_exceeded'`).

#### Public commitment type split + refusal pattern

- **BREAKING: `Commitment` is now a discriminated union `PublicVisibleCommitment | PublicHiddenCommitment`** — anonymous public reads of a `book_visible=false` commitment decode to `PublicHiddenCommitment` (allow-list-projected, no signature / nonce / odds / risk / scorer / lineTicks / speculationKey / marketType). New discriminants `visibility: 'visible' | 'hidden'`, `redacted: false | true`, and (for hidden) `payloadAvailable: false` — narrow on EITHER `c.visibility === 'visible'` or `c.redacted === false` to get the matchable payload. New predicate exports `isVisibleCommitment(c)` / `isHiddenCommitment(c)` for callers that prefer functions. The PUBLIC HIDDEN ALLOW-LIST is the contract — no upstream field addition can silently leak into the hidden public surface; the maker recovers the full payload via `client.ownState.snapshot({ address, cursor? })` (paged) or `client.ownState.getCommitment({ address, hash })` (snapshot-scope, see above).

Used by every write path that needs the matchable payload: `prepareMatch` (narrows at top, before contest fetch / chain read), `matchFromPreview` (narrow re-fetch before signer / RPC access), `cancelOnchain({ hash })` (fetches → `toCommitment` → `requireVisibleCommitment` BEFORE any signer / RPC / gas access — redacted public input throws without burning a keystore decrypt), `checkCommitmentFillability` (resolves + redaction short-circuits BEFORE `requireChainClient` / `getAddresses`, so the verdict resolves even for callers without an RPC config), `checkSubmitFundability` (degrades to `outcome: 'unknown'` with `FUNDABILITY_UNKNOWN` on hidden rows in the maker's open book — the redacted `remainingRiskAmount` would silently UNDER-count exposure otherwise). `submitRaw` / `submitPrepared` return `PublicVisibleCommitment` (submissions insert `book_visible=true` by construction; defensive narrow).
- **BREAKING: `commitments.cancelAllOnSpeculation({ ..., newMinNonce })` now requires an explicit `newMinNonce`** — interface-required AND runtime-validated (`OspexValidationError({ field: 'newMinNonce' })` on undefined or `<= 0`). ## [0.4.3] — 2026-05-25

### SDK (`@ospex/sdk`)

- **New `positions.ensurePositionClaimed({ speculationId, positionType })` — idempotent "make this claimed".** The claim-side mirror of `ensureSpeculationSettled`. Resolves to success whenever the position is claimed, returning `{ outcome: 'claimed' | 'alreadyClaimed' | 'recovered', payoutWei6?, … }`. It pre-flight-reads on-chain `getPosition.claimed` and skips the tx when already claimed, and recovers from a benign already-claimed that reverts mid-flight — a concurrent caller, a rerun, or core-API `claimable`-projection lag. Recovery is narrow by design: it fires on a decoded pre-send `AlreadyClaimed`, or on a claim that **provably reverted on inclusion** (the error carries a `'reverted'` receipt) **and** an on-chain re-read confirms `claimed` — never on a bare tx hash or a bare post-read. In particular, a tx that **succeeds** but whose `POSITION_CLAIMED` event can't be parsed stays a loud failure (the payout really happened; it must not be relabeled a no-payout recovery). **Only `AlreadyClaimed` is benign — `NotSettled`, `NoPayout`, and RPC/unknown errors stay loud.** Payout is event-sourced and present **only** on `outcome: 'claimed'`: the contract zeroes `riskAmount`/`profitAmount` once claimed, so `alreadyClaimed`/`recovered` carry no payout and the SDK never derives one. The strict `positions.claim` primitive is unchanged — it still sends a tx and throws `AlreadyClaimed`.
- **`OspexChainError` now carries the transaction `receipt`** when the failure occurred after the tx was mined (additive, optional). **Branch on `receipt.status`, not on presence:** `status === 'reverted'` is the authoritative on-chain-revert signal (carries `gasUsed`/`effectiveGasPrice` for accounting); `status === 'success'` may be attached on a post-send failure where the tx CONFIRMED but its result couldn't be read (e.g. a claim whose `POSITION_CLAIMED` event was unparseable); a `txHash` with no `receipt` means the on-chain status is unknown — **not** automatically reverted. This is what lets idempotent recovery (and the claim-all envelope) tell a real revert from a confirmed-but-unparseable claim.
- **`positions.claimAll`'s claim leg is now idempotent too.** Each row's claim leg runs through `ensurePositionClaimed`, so an already-claimed position (a prior run, a manual claim, a concurrent caller, `claimable`-projection lag) no longer fails that entry with `AlreadyClaimed` — it's skipped or recovered and the entry still counts as success. A genuine `NotSettled`/`NoPayout`/RPC failure still fails that entry clearly. A `failed` step now also records the broadcast tx's true on-chain status (`txStatus: 'confirmed' | 'reverted'`) so the agent envelope reports it honestly — a claim that confirmed on-chain but whose `POSITION_CLAIMED` event was unparseable surfaces as a `status:'confirmed'` (not `'reverted'`) effect.
- **New typed PositionModule revert classifiers** `isAlreadyClaimedRevert` / `isNotSettledRevert` / `isNoPayoutRevert`, exported from `@ospex/sdk`. They decode a caught claim error against the contract's custom-error selectors (selector + structured `errorName`, walking viem's nested cause chain) instead of matching message strings.

### CLI (`@ospex/cli`)

- **`ospex claim <speculationId> --type <…>` is now idempotent.** It routes through `ensurePositionClaimed`, so re-claiming an already-claimed position reports success (`outcome: alreadyClaimed` — no tx, no payout, no `AlreadyClaimed` revert) instead of erroring. It pre-flight-reads on-chain state and skips the tx when already closed, and recovers from a concurrent settle that reverts mid-flight (the recover/abort decision is an authoritative on-chain re-read, so it tolerates core-API `pendingSettle` projection lag). - **`positions.claimAll` is now projection-aware.** Each `pendingSettle` row's settle leg runs through `ensureSpeculationSettled`, so a stale `pendingSettle` plan whose speculation was already settled (e.g. by another wallet seconds earlier) no longer fails with a pre-send duplicate-settle error — the settle is skipped or recovered and the sweep proceeds to claim. When multiple wallets sweep close together, at most one settle tx lands. Each entry now carries an explicit `steps[]` record (`sent` / `skippedAlreadySettled` / `recoveredAlreadySettled` / `failed`); `txHashes` / `winSide` / `payout*` are conveniences derived from it. A genuine settle failure (not already-settled) still fails that entry clearly, and dry-run remains read-only (no chain reads).

### CLI (`@ospex/cli`)

- **`ospex claim-all` absorbs projection lag quietly.** A skipped or recovered settle is reported as a normal success with a short `[settle skipped — already settled]` note, and under `--json` as an `info`-severity warning (`settle-skipped-already-settled` / `projection-lag-recovered`) — not a scary failure. The `--json` envelope's per-tx effects are now driven by the SDK's explicit `steps[]`, fixing a latent mislabel where a skipped-settle entry's lone claim tx could be tagged as a settle. A settle tx that actually reverts on chain — whether a genuine failure or a lost race that recovered — keeps its hash in `effects[]` with `status: 'reverted'`, so gas-spending failures stay auditable.
- **`ospex settle <id>` is now idempotent.** It routes through `ensureSpeculationSettled`, so re-settling an already-settled speculation reports success (`outcome: alreadySettled` — no tx, no `AlreadySettled` revert) instead of erroring. Output now carries the `outcome`; under `--json`, `alreadySettled` / `recovered` emit an `info` warning with empty `effects[]`, and a recovered race that broadcast a reverted settle surfaces it as a `status:'reverted'` effect. The strict `client.positions.settleSpeculation` (always sends a tx; throws `AlreadySettled`) stays available for programmatic callers.

Apply last-received-wins per natural key (the cursor is an opaque resume token, never an ordering key).

- **New `OspexStreamError`** (`reason: connection_failed | capacity_exceeded | fatal`) — distinct from the Chainlink-Functions `OspexSubscriptionError`. Delivered to `onError`; `fatal` ends the subscription, the others are retried.

- `ospex positions {list, status, history}` plus top-level `claim`, `claim-all`, `settle` (registered at the program root for day-to-day ergonomics, not under `positions`) with `--dry-run` on `claim-all` and `cancel-all`.
- `ospex odds {show, watch}` — one-shot snapshot + Realtime stream (line-delimited JSON in `--json` mode).
- `ospex leaderboard show`.
- `ospex wallet {import, address, unlock, lock}` — legacy session-cache path.
- Most commands support `--json` for machine-readable output; the interactive setup / wallet-management flows (`init`, `wallet import`, `wallet unlock`, `wallet lock`) do not. See [`docs/AGENT_CONTRACT.md`](./docs/AGENT_CONTRACT.md) for the stable agent contract.

### Known limitations

- Tarball-only distribution (no npm publication). Both `ospex-sdk-<ver>.tgz` and `ospex-cli-<ver>.tgz` must be installed in the same `yarn add` call.
- Cross-process nonce coordination is not provided — submits distributed across hosts must serialize nonce assignment per `(maker, speculationKey)`.
- Realtime channels do not replay missed events on reconnect — re-poll snapshots if you need a known-good baseline.
- Contest creation is mainnet-only; Polygon Amoy script approvals are not committed.
